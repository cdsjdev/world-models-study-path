Phase 1 · Topic 05

Cosmos Architecture

Where every concept from the last four topics actually lives in the Cosmos Framework codebase: Reasoner vs. Generator, inference vs. training, and the file paths you'll actually touch in Phase 2.

This topic is different from the other four

Video representations, world models, multimodal grounding, and evaluation are field-wide concepts: they'd be true regardless of which specific model or framework you used. This topic is deliberately narrower: it's a map of one specific, real codebase, so that when Phase 2 asks you to install and run Cosmos, you already know where things live instead of exploring blind.

Reasoner versus Generator

Cosmos 3 exposes two runtime surfaces within a unified omnimodal Mixture-of-Transformers architecture. They are modes with different attention behavior and outputs, not simply two unrelated model families:

Cosmos Reasoner

  • Text and vision in; text out (JSON only when requested and successfully followed)
  • Understanding, grounding, physical reasoning, planning, and action forecasting
  • Example inputs live at inputs/reasoner/*.json

Cosmos Generator

  • Text, vision, sound, or action conditions in; vision, synchronized sound, or action out
  • Generation, simulation, future prediction, synthetic data, and policy learning
  • Example inputs live at inputs/omni/*.json (e.g. t2v.json for text-to-video)

The two surfaces share the Cosmos 3 transformer architecture, multimodal attention layers, and 3D multidimensional rotary position encoding. Reasoner mode uses causal self-attention for autoregressive text prediction; Generator mode uses full attention to denoise multimodal tokens. Available modalities still depend on the selected checkpoint and serving backend.

Inference versus training: two separate trees

The codebase enforces the inference/training split structurally, not just conceptually: the repo's own contributor guidance is explicit that inference-time code and training-time code should not import from each other. This matters for Phase 2: everything you need for reproducible inference lives under cosmos_framework/inference/, and you do not need to read the training subpackages at all yet.

Distributed execution

Both inference and training scale from a single GPU to multiple nodes using the same underlying pattern: a launcher (torchrun for single-node multi-GPU, Slurm or k8s for multi-node) starts multiple processes that coordinate through a parallelism strategy defined in cosmos_framework/model/. For inference specifically, a --parallelism-preset flag (e.g. latency) selects a tuned configuration rather than requiring you to hand-tune parallelism dimensions yourself.

This connects to the evaluation topic's latency and cost metrics: the parallelism preset you choose is a direct lever on both. A latency-tuned preset trades GPU-hours for faster single-request turnaround: the right trade-off depends on whether you're optimizing for one urgent event or high-throughput batch processing of many clips.

Commands you'll actually run in Phase 2

These are pulled directly from the framework's own contributor guidance, not paraphrased: they are the real commands, kept here so Phase 2 starts from a known-working baseline instead of trial and error.

TaskCommand
Single-GPU inference python -m cosmos_framework.scripts.inference -i inputs/omni/t2v.json -o outputs/ --checkpoint-path Cosmos3-Nano
Multi-GPU inference torchrun --nproc-per-node=4 -m cosmos_framework.scripts.inference --parallelism-preset=latency -i ... -o outputs/ ...
Start online Ray server python -m cosmos_framework.inference.ray.serve --parallelism-preset=latency -o outputs/ray_serve --checkpoint-path Cosmos3-Nano
See all CLI flags python -m cosmos_framework.scripts.inference --help
Two gotchas worth knowing before Phase 2 Reproducibility requires explicitly passing --seed <int>: without it, a random seed is used every run, which breaks the "one fixed experiment" goal from Phase 2. And relative paths inside input JSON files resolve relative to the JSON file's own directory, not your current working directory: a common source of confusing "file not found" errors.
