Evaluation

A model that looks impressive in a demo and a model that is trustworthy in production are judged by different numbers. This topic is the measurement discipline that keeps the rest of the study path honest.

Why evaluation is its own topic

Every capability introduced so far: representation, prediction, multimodal grounding: can fail silently. A video model can produce a fluent, confident, wrong answer. A generator can produce a beautiful, physically implausible clip. Without a measurement discipline, the only signal you have is does this look right to me, which does not scale, does not catch rare failure modes, and does not transfer between people. Evaluation is what turns "looks good" into a number you can track, compare, and set a gate on.

Temporal grounding

Temporal grounding measures whether a model's claim about when something happened in a video is actually correct: not just whether it correctly describes that something happened. If a model reports "a vehicle stopped in the lane" with an evidence timestamp of 0:14–0:19, temporal grounding asks: did the vehicle actually stop during that window, or is the model pattern-matching a plausible-sounding timestamp onto a real event that happened somewhere else in the clip?

It is typically measured with Intersection over Union (IoU) between the model's predicted time span and the ground-truth time span, thresholded at some minimum overlap (e.g. IoU ≥ 0.5 counts as "grounded correctly"). This matters enormously for an operator-review workflow: an operator who is handed the wrong ten seconds of footage to review has effectively been given a false lead.

Event recall, precision, and false-alarm rate

These three metrics form the core of any detection-style evaluation and are best understood together, because optimizing any one in isolation is easy and usually wrong.

MetricQuestion it answersFailure if ignored
Recall Of all real events, what fraction did the model catch? A model that stays silent scores perfect precision but is useless.
Precision Of everything the model flagged, what fraction was real? A model that flags everything scores perfect recall but drowns operators in noise.
False-alarm rate How often does the model raise an alert with nothing real behind it, per unit of time or per clip? Directly determines whether operators start ignoring the system (alert fatigue).

Recall and precision trade off against each other through the model's confidence threshold: reporting more events raises recall and lowers precision, and vice versa. This is exactly why single-number summaries (like accuracy) are misleading for event detection, and why a real evaluation reports the trade-off curve, or fixes an operating point and reports both numbers at that point.

Calibration

If you bucket all predictions where the model said "80% confident" and check how often those predictions were actually correct, a well-calibrated model should be right about 80% of the time in that bucket. A poorly calibrated model might say 80% confident and be right only 40% of the time: overconfident: or say 80% and be right 98% of the time: underconfident.

This is not a cosmetic detail. A downstream system that supports an uncertain result and routes it to human review is only as good as the calibration of the confidence score driving that routing: miscalibration either buries real events under "confident" wrong answers or floods operators with unnecessary reviews of predictions that were actually fine.

Robustness

Robustness measures how much performance degrades under conditions that differ from the training distribution: lighting changes, camera angle, weather, sensor noise, compression artifacts, or an unfamiliar location. A model evaluated only on clean, well-lit, familiar footage tells you almost nothing about how it will perform on the messy real-world clips it will actually receive in production.

Robustness is typically reported as a performance delta: accuracy on a clean held-out set minus accuracy on a stress-test set built from deliberately harder conditions. This is also where the multimodal topic's synthetic-data caution reconnects: synthetic night/rain/fog variants are tempting robustness test data, but only if you've already confirmed the generator's variants are physically representative, not just visually plausible.

Latency and cost

A model can be accurate, well-calibrated, and robust and still be operationally useless if it is too slow or too expensive to run at the required scale. These two metrics are the ones most often skipped in a research-oriented evaluation and most often decisive in an operational one.

  • Latency: end-to-end time from clip arrival to structured output, broken down by stage (upload, inference, postprocessing) so you know where time is actually spent.
  • Cost: GPU-time or dollar cost per event evaluated, which determines whether a promising accuracy number is actually affordable to run continuously at the target scale (e.g. 10-20 poles running around the clock).

Composing the metrics into a gate

No single metric above is sufficient on its own: the discipline is in reading them together as a profile, not cherry-picking the best-looking number. A useful mental model: recall and precision describe whether the model finds the right things; calibration describes whether you can trust its confidence when it does; robustness describes whether that performance holds up outside the clean test set; latency and cost describe whether any of it is deployable.

Study checklist

Before moving on, you should be able to
  • Explain the difference between temporal grounding and simple event detection.
  • Describe why recall, precision, and false-alarm rate must be read together.
  • Explain what it means for a model to be overconfident versus underconfident.
  • Name all five metric families and put them in the order you'd check them for a new model.
